# Delta Specification: UI/UX de la app movil Flutter

**Change**: `app-movil-flutter-ui-ux`  
**Scope**: `flutter/` only  
**Base spec**: `openspec/specs/app-movil-flutter/spec.md`  
**Approved proposal**: `openspec/changes/app-movil-flutter-ui-ux/proposal.md`

## Purpose

This delta spec updates the Flutter mobile application from a functional prototype to a professional, accessible, and visually consistent mobile experience. It preserves the existing architecture (Clean Architecture, Riverpod, GoRouter `StatefulShellRoute` per ADR-3, `DateTime`/converters per ADR-9) and does not change backend contracts, business logic, or the web frontend.

## ADDED Requirements

### R1 [DESIGN-SYSTEM] Three-layer design tokens

The system MUST expose a centralized Design System in `flutter/lib/presentation/theme/` using three token layers: primitive, semantic, and component. Widgets MUST consume semantic or component tokens; they MUST NOT use hardcoded colors, spacing, typography sizes, border radii, elevations, or icon sizes.

#### Scenario: Primitive tokens define raw values

- GIVEN the app needs a color, spacing, radius, elevation, typography size, or icon size
- WHEN a developer inspects the theme files
- THEN primitive tokens (e.g., `AppColors.blue700`, `AppSpacing.space16`, `AppRadii.radiusM`) exist as the single source of truth for raw values

#### Scenario: Semantic tokens adapt to light/dark

- GIVEN the app runs in light or dark mode
- WHEN a widget requests a semantic color (e.g., `AppColors.primary`, `AppColors.surface`, `AppColors.error`)
- THEN the value resolves to the correct primitive for the active `ThemeMode`

#### Scenario: Component tokens centralize reusable styles

- GIVEN the app renders Cards, AppBars, Buttons, Inputs, NavigationBars, Dialogs, BottomSheets, or SnackBars
- WHEN those components are styled
- THEN they use component-level tokens (e.g., `AppComponentStyles.cardPadding`, `AppComponentStyles.buttonHeight`, `AppComponentStyles.appBarElevation`) instead of inline values

#### Scenario: No hardcoded styles in new widgets

- GIVEN a new widget is added during this change
- WHEN `flutter analyze` runs and a token audit is performed
- THEN no raw hex colors, magic numbers for spacing, raw `TextStyle` font sizes, or hardcoded elevations appear outside the token files

### R2 [THEME-SELECTOR] Visible theme selector

The system MUST provide a visible theme selector in `Más > SISTEMA` with three options: Claro, Oscuro, and Seguir sistema. The default selection MUST follow the system preference. The selected mode MUST persist across app restarts using a local preference store (no backend dependency).

#### Scenario: Default follows system

- GIVEN the device is set to dark mode and the user has not changed the app preference
- WHEN the app launches
- THEN the app renders in dark mode and the selector shows "Seguir sistema"

#### Scenario: User selects light mode

- GIVEN the user opens `Más > SISTEMA`
- WHEN they select "Claro"
- THEN the app switches to light mode immediately and persists the choice

#### Scenario: User selects dark mode

- GIVEN the user opens `Más > SISTEMA`
- WHEN they select "Oscuro"
- THEN the app switches to dark mode immediately and persists the choice

#### Scenario: Return to system default

- GIVEN the user previously selected "Claro"
- WHEN they select "Seguir sistema"
- THEN the app reverts to the device theme and clears the manual override

The splash screen MUST display the same motif on launch.

#### Scenario: Splash screen shows FerrePlus hardware motif

#### Scenario: Fallback reproducible icon generation

### R4 [DASHBOARD-KPI] Six KPI cards matching the web dashboard

The system MUST render six KPI cards on the dashboard using the same data and semantics as the web dashboard:

1. **Total Productos** — `inventory_2`, `#1565C0`, route `/productos`
2. **Stock Bajo** — `warning_amber`, `#c62828`, route `/productos`
3. **Ventas Hoy** — `today`, `#2e7d32`, route `/ventas`
4. **Ventas del Mes** — `date_range`, `#FF8F00`, route `/ventas`  
   (#FF8F00 falla contraste 4.5:1 en claro; implementado con kpiAmberAccessible #B45309 por R16)
5. **Total Clientes** — `people`, `#6a1b9a`, route `/clientes`
6. **Proveedores** — `local_shipping`, `#00838f`, route `/proveedores`

Each KPI card MUST display a Material icon, a label, and a value. The semantic color MUST apply only to the icon or a small badge; the card background MUST remain neutral. The value text MUST have greater visual weight than the label. Tapping a card MUST navigate to its associated route.

#### Scenario: Dashboard renders all six KPIs

- GIVEN the backend returns a `ReporteDashboard` with all fields populated
- WHEN the user opens the dashboard
- THEN the six KPI cards appear with the correct icon, label, and value

#### Scenario: KPI colors are semantic and contained

- GIVEN the dashboard is rendered
- WHEN a KPI card is inspected
- THEN only the icon (or a small badge) uses the semantic color; the card surface uses the theme surface color

#### Scenario: KPI tap navigates to route

- GIVEN the user is on the dashboard
- WHEN they tap "Total Clientes"
- THEN the app navigates to `/clientes`

#### Scenario: KPI value is more prominent than label

- GIVEN the dashboard is rendered
- WHEN a KPI card is inspected
- THEN the numeric value uses a larger/heavier type style than the label

### R5 [DASHBOARD-CHART] Sales chart by period

The system MUST render a simple bar chart of sales by period on the dashboard. The selector MUST offer three periods: "Esta Semana", "Este Mes", and "Este Año". The chart MUST use the existing `ReporteDashboard.ventasPorDia` data or call the same endpoint the web uses to obtain ventas by date (`ReporteRepository.ventas(desde, hasta)`), group the results by day when period is week/month or by month when period is year, and render bars using only Flutter built-in widgets (`CustomPaint`, `Row` of `Container`, or similar). No new chart library dependency MAY be added.

#### Scenario: Default period is month

- GIVEN the user opens the dashboard
- WHEN the chart section loads
- THEN the selector shows "Este Mes" and the chart displays sales grouped by day for the current month

#### Scenario: Switch to week

- GIVEN the dashboard chart is visible
- WHEN the user selects "Esta Semana"
- THEN the chart recomputes the date range from the current Monday to today and displays sales grouped by day

#### Scenario: Switch to year

- GIVEN the dashboard chart is visible
- WHEN the user selects "Este Año"
- THEN the chart recomputes the date range from January 1 to today and displays sales grouped by month

#### Scenario: Chart formats values as currency

- GIVEN the chart has data
- WHEN the user views the bars
- THEN values are formatted with the app's currency formatter (e.g., "$1,250.00")

#### Scenario: Empty chart state

- GIVEN the selected period has no sales
- WHEN the chart renders
- THEN it shows an empty state message such as "Sin ventas registradas en el periodo" instead of inventing data

### R7 [DASHBOARD-STATES] Dashboard loading, empty, and error states

On error, it MUST show an error message and a retry CTA. On empty `ReporteDashboard` (all zero/empty values), it MUST show an empty state with a message and, if permitted, a CTA to create initial data.

#### Scenario: Dashboard loading

- GIVEN the dashboard request is in flight
- WHEN the dashboard renders
- THEN a skeleton/shimmer placeholder for KPIs and chart is shown

#### Scenario: Dashboard error with retry

- GIVEN the dashboard request fails
- WHEN the dashboard renders
- THEN an error message appears together with a "Intentar nuevamente" button

#### Scenario: Dashboard empty

- GIVEN the backend returns a `ReporteDashboard` with all counters at zero and no chart data
- WHEN the dashboard renders
- THEN an empty state message appears (e.g., "Bienvenido a FerrePlus — los datos de tu negocio aparecerán aquí")
- AND no fake data is displayed

### R16 [A11Y] Accessibility compliance

The system MUST meet the following accessibility requirements: contrast ratio of at least 4.5:1 for text and icons; touch targets of at least 48 dp for all interactive controls; semantic labels (`Semantics` or `tooltip`) for all icon-only buttons; support for system text scaling without clipped text; and no information conveyed by color alone.

#### Scenario: Contrast meets minimum

- GIVEN the app runs in light or dark mode
- WHEN foreground text/icons are measured against their background
- THEN the contrast ratio is at least 4.5:1

#### Scenario: Touch targets meet minimum

- GIVEN an interactive control (button, icon button, list tile, chip)
- WHEN its hit area is measured
- THEN it is at least 48 dp × 48 dp

#### Scenario: Icon buttons have labels

- GIVEN an icon-only button (e.g., AppBar action, FAB)
- WHEN a screen reader focuses it
- THEN it announces a descriptive label

#### Scenario: Text scale support

- GIVEN the device text scale is set to the largest accessible setting
- WHEN the dashboard renders
- THEN text wraps or scrolls instead of overflowing or clipping

#### Scenario: Color is not the only indicator

- GIVEN a status or state indicator uses color
- WHEN the indicator is viewed in grayscale
- THEN a second visual cue (icon, text, pattern) still conveys the meaning

## REMOVED Requirements

### R-X1 [BASE-SPEC R8] 15-destination NavigationBar

The previous implementation in `shell_scaffold.dart` that rendered up to 15 items in a single `NavigationBar` is REMOVED. The NavigationBar MUST NOT contain more than five destinations. All previously reachable routes remain accessible via `Más` or deep links.

**Reason**: Material Design recommends a maximum of five bottom-navigation destinations; 15 items caused overflow, label wrapping, and poor discoverability.

---

### R-X2 [BASE-SPEC R43] Generic Flutter launcher icon

The default Flutter launcher icon and splash are REMOVED. They are replaced by the FerrePlus `hardware` motif per R3.

**Reason**: The app must present a professional FerrePlus identity consistent with the web brand.

---

## NOT Requirements / Out of Scope

The following items are explicitly NOT part of this change:

- **Backend changes**: no new endpoints, no DTO changes, no business logic changes, no database schema changes.
- **Frontend changes**: the web Angular frontend is not modified.
- **New chart library**: the sales chart MUST use only Flutter built-in widgets (`CustomPaint`, `Container`, etc.). `fl_chart` is already present but no new dependency is added for charts.
- **New dashboard data**: the dashboard MUST render only the fields already provided by `ReporteDashboard` (`ventasHoy`, `ventasMes`, `totalComprasMes`, `totalGastosMes`, `productosStockBajo`, `ventasPorDia`, `totalClientes`, `totalProveedores`, `saldoPendienteClientes`, `totalProductos`, etc.). No new endpoints or derived metrics are created.
- **ADR changes**: ADR-3 (GoRouter + `StatefulShellRoute`) and ADR-9 (`DateTime` with ISO converters) remain unchanged.
- **Push notifications, offline sync, or background sync**.
- **Redesign of authentication flow or chat business logic**.
- **New roles/permissions model**; visibility continues to be based on the existing `Set<String>` of permission codes.
